# 루프 작업 절차

Claude가 `/loop`로 RobinOS를 이어서 만들 때 회차마다 따르는 순서예요. 작업 목록은 [tasks.md](tasks.md), 검사 방법은 [testing.md](testing.md), 저장소 규칙은 [../CLAUDE.md](../CLAUDE.md)에 있어요.

## 시작하기

Claude Code에서 간격 없이 실행해요. 그러면 Claude가 작업에 맞춰 다음 회차 시각을 정해요.

```text
/loop docs/loop.md 절차대로 RobinOS 작업을 한 회차 진행해
```

**루프는 스스로 멈추지 않아요.** 할 일이 떨어지면 새 일을 찾아 채우고, 막힌 일은 제쳐 두고 다른 일을 해요. 멈추려면 루프를 취소하거나 "루프 멈춰"라고 말하면 돼요.

## 한 회차의 크기

- 한 회차에 작업 하나를 끝내거나, 큰 작업이면 빠른 검사까지 할 수 있는 한 조각을 끝내요. 느린 검증(ISO 빌드, VM 테스트)은 여러 작업을 모아서 해요(아래 "5. 검증").
- 회차가 끝날 때 작업 트리는 깨끗해야 해요. 검사를 통과한 변경은 커밋하고, 통과하지 못한 반쪽 변경은 남기지 않아요(되돌리거나 더 작게 마무리해요).
- 긴 빌드나 VM 테스트는 백그라운드로 띄우고, 기다리는 동안 다른 일을 하거나 회차를 마쳐요. 결과는 다음 회차에 거둬요.
- 대화가 길어져 앞부분이 요약돼도 괜찮아요. 루프의 기억은 [tasks.md](tasks.md)와 git 기록이에요. 회차마다 거기서 다시 시작해요.

## 회차 순서

### 1. 상황 파악

```powershell
git status --short
git log --oneline -5
git log --oneline origin/main..HEAD
powershell -ExecutionPolicy Bypass -File scripts/wsl-build.ps1 status
```

그다음 [tasks.md](tasks.md)를 읽어요. 백그라운드 작업, 정기 점검, 푸시 대기 커밋, 사용자 확인 필요, 진행 중인 작업 순서로 봐요. 작업 트리에 이전 회차가 남긴 변경이 있으면 그것부터 정리해요.

### 2. 끝난 결과 거두기

`status`에 아무것도 돌고 있지 않은데 tasks.md에 `실행 중`인 백그라운드 작업이 있으면, 그 작업이 끝난 거예요.

- 부팅 테스트: `build\boot-test\*.png`를 한 장씩 열어 봐요. `serial.log`에서 `robinos-session`, `quickshell`, `qml`, `Failed`를 찾아요.
- 설치 테스트: `build\install-test\*.png`와 `serial-live.log`, `serial-installed.log` 끝부분에서 `[install-test] FAILED`나 `passed`를 찾아요.
- ISO 빌드: WSL의 `/root/RobinOS/out/`과 `build/logs/`의 마지막 로그를 봐요.

결과를 tasks.md에 적어요. 통과했으면 해당 작업과 푸시 대기 커밋을 갱신하고, 실패했으면 원인을 찾아서 고칠 일을 `진행 중`으로 올려요. 같은 실패가 세 번 반복되면 그 작업은 `막힘`으로 두고, 원인과 시도한 것을 적은 뒤 다른 작업으로 넘어가요.

### 3. 작업 고르기

이 순서로 골라요.

1. 방금 거둔 결과에서 나온 실패 고치기
2. `진행 중`인 작업
3. 정기 점검이 밀렸으면 정기 점검 (아래 "정기 점검")
4. `할 일`의 맨 위 작업 (`막힘`은 건너뛰어요)
5. 할 일이 없거나 전부 `막힘`이면 **백로그 채우기**(아래)로 새 작업을 만들고 그 맨 위 작업

WSL에서 백그라운드 작업이 돌고 있으면 WSL 클론을 건드리는 일(빌드, 부팅 테스트, 설치 테스트)은 시작할 수 없어요. 그동안은 윈도우 쪽에서 할 수 있는 일을 해요. 코드 작성, `scripts/validate-project.ps1`, `scripts/wsl-build.ps1 check`(qmllint 포함), 문서 정리, 백로그 채우기 같은 일이에요.

### 4. 만들기

- 둘레 코드의 말투와 구조를 따라요. 사용자에게 보이는 글은 한국어(해요체)예요.
- `desktop/`, `bin/`, `scripts/`, `docs/`, `themes/`를 바꾸면 `scripts/sync-archiso-files.ps1`로 ISO 오버레이를 맞춰요. 이 스크립트가 바꾸는 `archiso/airootfs/etc/sddm.conf.d/10-robinos-theme.conf`의 줄 끝(CRLF)은 `git checkout`으로 되돌려요.
- 새 스크립트는 `git update-index --chmod=+x`로 실행 권한을 기록해요.
- 설계를 정해야 하면 직접 정하고 [design.md](design.md)에 결정과 이유, 날짜를 적어요. 제품 방향을 크게 바꾸는 결정만 사용자에게 넘겨요(아래 "사용자에게 넘길 때").

### 5. 검증

[testing.md](testing.md) 맨 위의 표대로 검사를 골라요.

- 빠른 검사(정적 검증, `bash -n`, `wsl-build.ps1 check`)는 그 자리에서 돌려요.
- **느린 검증은 모아서 한 번에 해요.** 작업마다 ISO를 빌드하지 않아요(2026-10-08 사용자 요청: "많이 작업해서 빌드하기"). 빠른 검사를 통과한 작업은 커밋해서 푸시 대기 표에 올리고 다음 작업으로 넘어가요. 작업이 3~5개 쌓였거나 더 할 만한 일이 없을 때, ISO 빌드, 부팅 테스트, 그리고 필요하면 설치 테스트를 한 번 돌려 쌓인 커밋을 함께 검증하고 함께 푸시해요. 보통은 `wsl-build.ps1 verify -Installer robinos` 하나로 해요(빠른 zstd ISO를 빌드하고 부팅 테스트와 설치 테스트를 동시에 돌려요). 릴리스용 ISO만 `build`로 xz 압축해요.
- ISO 빌드, 부팅 테스트, 설치 테스트는 먼저 커밋한 뒤(WSL은 HEAD를 가져가요) 백그라운드로 띄우고, 도는 동안에는 기다리지 말고 다음 작업을 해요(테스트가 읽는 `scripts/`의 테스트 파일만 끝날 때까지 건드리지 않아요). 그리고 tasks.md의 백그라운드 작업 표에 시작 시각, 대상 커밋, 결과 위치를 적어요.
- 빌드와 테스트를 이어서 돌릴 때는 `build`가 끝난 뒤 `boot-test`처럼 차례로 해요. 한 번에 하나만 돌릴 수 있어요.

걸리는 시간 (이 PC, 윈도우 10 WSL 2 기준):

| 작업 | WHPX (기본) | TCG (Windows용 QEMU가 없을 때) |
|---|---|---|
| ISO 빌드 (처음부터) | 9분 (2026-10-08 측정, VM 아님) | 같음 |
| 부팅 테스트 | 3분 30초 (2026-10-08 측정) | 6분 (2026-10-07 측정) |
| 설치 테스트 (archinstall) | 10분 (2026-10-08 측정, 인터넷 속도에 따라 달라요) | 1시간 넘을 수 있음 |

새로 잰 시간은 이 표에 고쳐 적어요.

### 6. 기록

- [tasks.md](tasks.md): 작업 상태, 백그라운드 작업, 정기 점검, 푸시 대기 커밋, 끝난 일(완료 목록 맨 위에 날짜와 커밋)
- [design.md](design.md): v0.1 항목 상태가 바뀌었거나 새 설계 결정을 했을 때
- 그 밖의 문서: [README.md](README.md)의 "같이 고칠 문서" 표를 따라요

### 7. 커밋

- 작업 단위로 커밋해요. 메시지는 한국어로, 첫 줄은 무엇을 했는지, 본문은 왜 그렇게 했는지 써요. 끝에 `Co-Authored-By` 줄을 붙여요.
- 커밋하기 전에 `scripts/validate-project.ps1`은 꼭 통과해야 해요.

### 8. 푸시

`git log origin/main..HEAD`의 모든 커밋이 필요한 검증을 통과했을 때(tasks.md의 푸시 대기 표가 비었을 때) `git push origin main`을 해요. 문서만 바꾼 커밋은 정적 검증이면 충분해요. 앞에 검증을 기다리는 커밋이 있으면 함께 기다려요. GitHub Actions는 수동 실행 전용이라 푸시해도 돌지 않아요.

### 9. 보고

회차 끝에 한국어로 짧게 알려요.

```text
이번 회차: <한 일>
검증: <돌린 검사와 결과, 백그라운드로 띄운 것>
다음: <다음 회차에 할 일>
사용자 확인 필요: <있을 때만>
```

### 10. 다음 회차 예약

**회차는 언제나 `ScheduleWakeup`으로 끝나요.** 오류가 났거나, 검증이 실패했거나, 할 일이 없어 보여도 마찬가지예요. 같은 `/loop` 문장을 그대로 넘겨요.

| 상황 | 기다릴 시간 |
|---|---|
| 바로 이어서 할 일이 있음 (백로그를 막 채운 경우 포함) | 60초 |
| ISO 빌드를 기다림 | 600초 |
| 부팅 테스트를 기다림 | 240초 |
| ISO 빌드 + 부팅 테스트를 이어서 기다림 | 840초 |
| 설치 테스트를 기다림 | 1800초, 끝나지 않았으면 다시 1800초 |
| 지금 당장은 아무것도 할 수 없음 (WSL 장애 등) | 1800초 |

기다리는 동안 할 일이 남아 있으면 기다리지 말고 그 일을 해요.

## 백로그 채우기

`할 일`이 비었거나 전부 `막힘`이면 아래 출처를 위에서부터 훑어서 새 작업을 3~5개 만들어요. 앞쪽 출처에서 쓸 만한 일이 나오면 뒤쪽은 보지 않아도 돼요.

1. **v0.1 범위**: [design.md](design.md) v0.1 표에서 "완료"가 아닌 항목의 남은 구현, 검증, 문서
2. **검증이 빠진 기능**: tasks.md 완료 목록에 "VM 검증 전"이 붙은 것, 자동 테스트가 없는 기능(부팅 테스트에 장면 추가, 설치 테스트에 시나리오 추가)
3. **화면 다듬기**: 가장 최근 부팅·설치 테스트 스크린샷에서 보이는 문제. 잘리거나 겹치는 글자, 어색한 여백, 영어로 남은 문구, 다크·라이트 불일치, [design.md](design.md)의 shadcn/ui 기준과 다른 곳
4. **학습 기능 늘리기**: [design.md](design.md) 학습 설계를 따라요. 미션 추가(네트워크 기초, 웹 보안), 실습 랩 추가(네트워크 스캔 랩, 로컬 CTF), 윈도우 명령 힌트와 런처 윈도우 이름 넓히기
5. **로드맵 다음 단계**: [roadmap.md](roadmap.md)에서 끝나지 않은 항목 (3단계 보안 프로필, 6단계 공개 프리뷰 준비 등)
6. **품질 점검**: 아래 영역 중 tasks.md "품질 점검 기록"에서 가장 오래전에 본 영역 하나를 골라 훑고, 찾은 문제를 작업으로 만들어요.
   - 코드 검토: 버그, 오류 처리, `set -e` 함정, 경계 조건 (`robinctl`, `robin-install`, 셸 QML을 파일 단위로)
   - 문서와 코드 맞추기: 문서에 적힌 명령, 경로, 단축키가 실제와 같은지
   - 보안과 윤리: 랩이 `127.0.0.1`에만 열리는지, 라이브 ISO의 기본 비밀번호와 원격 접속, sudo 설정, [ethics.md](ethics.md)와 맞는지
   - 접근성: 키보드만으로 셸을 다 쓸 수 있는지, 글자 대비, 스크린 리더 이름(`Accessible.name`)
   - 성능: 소프트웨어 렌더링(VM)에서 셸 효과와 애니메이션, 부팅 시간
   - 업스트림 변화: Arch 패키지 이름, Hyprland·Quickshell 새 버전에서 설정과 QML 검사
7. **v0.2 후보**: tasks.md T-011. v0.1 범위가 다 끝났을 때만 꺼내요.

새 작업을 만들 때 지킬 것:

- 형식은 다른 작업과 같아요: 번호(`T-` 다음 번호), 목표, 완료 기준, 검증 방법, 출처(예: "출처: 품질 점검 - 문서와 코드").
- 제품 목표([design.md](design.md)의 설계 원칙)에 도움이 되는 일만 넣어요. 이유 없는 이름 바꾸기나 서식 정리 같은 바쁜 일은 넣지 않아요.
- 한 작업은 1~3회차에 끝낼 크기로 쪼개요.
- 품질 점검을 했으면 결과가 없어도 tasks.md "품질 점검 기록"에 날짜를 남겨요. 그래야 같은 영역만 계속 보지 않아요.
- 제품 방향을 크게 바꿔야 할 일이 보이면 "사용자 확인 필요"에 적고, 그동안 다른 작업을 해요.

## 정기 점검

기능 작업만 하다 보면 이미 된 것이 모르는 새 깨질 수 있어요. 그래서 주기적으로 처음부터 다시 확인해요.

- 언제: tasks.md "정기 점검"의 마지막 날짜가 하루 넘게 지났거나, 그 뒤 커밋이 10개 넘게 쌓였을 때
- 무엇을: 정적 검증, `wsl-build.ps1 check`, ISO 빌드(패키지 검사 포함), 부팅 테스트. 설치 테스트는 일주일에 한 번, 또는 설치·복구 코드를 바꿨을 때
- 기록: tasks.md "정기 점검"에 날짜, 대상 커밋, 결과를 적어요. 깨진 게 있으면 고칠 일을 `진행 중`으로 올려요.

## 사용자에게 넘길 때

이런 일은 직접 하지 않아요. tasks.md의 "사용자 확인 필요"에 적고, 보고에서 알리고, **다른 작업을 계속해요.** 사용자 답을 기다리느라 루프를 세우지 않아요.

- 관리자 권한이 필요하거나 윈도우 시스템 설정을 바꾸는 일
- 실기기 테스트처럼 사용자만 할 수 있는 일
- `git push --force`, 히스토리 다시 쓰기, 브랜치나 릴리스 지우기
- 돈이 들거나 계정 설정을 바꾸는 일
- 제품 방향을 크게 바꾸는 결정 (대상 사용자, 기반 배포판, 데스크톱 교체 같은 것)

개발 도구를 공식 출처에서 내려받는 건 괜찮아요. 내려받은 뒤 체크섬을 확인해요.

## 막혔을 때 이어 가는 법

- 작업이 막히면 `막힘`으로 두고 이유와 시도한 것을 적은 뒤 다른 작업을 골라요. 막힌 작업은 회차마다 다시 보지 않고, 상황이 바뀌었을 때(관련 코드나 환경이 달라졌을 때) 다시 꺼내요.
- 도구가 실패하면 우회해요. WSL이 응답하지 않으면 `wsl --shutdown` 뒤 다시 해 보고, 그래도 안 되면 윈도우 쪽에서 할 수 있는 작업을 해요.
- 사용자가 멈추라고 하기 전까지 루프를 끝내지 않아요. 할 수 있는 게 정말 없어 보이면 백로그 채우기를 다시 해요. 품질 점검 영역은 늘 남아 있어요.
