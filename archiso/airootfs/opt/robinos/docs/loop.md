# 루프 작업 절차

Claude가 `/loop`로 RobinOS를 이어서 만들 때 회차마다 따르는 순서예요. 작업 목록은 [tasks.md](tasks.md), 검사 방법은 [testing.md](testing.md), 저장소 규칙은 [../CLAUDE.md](../CLAUDE.md)에 있어요.

## 시작하기

Claude Code에서 간격 없이 실행해요. 그러면 Claude가 작업에 맞춰 다음 회차 시각을 정해요.

```text
/loop docs/loop.md 절차대로 RobinOS 작업을 한 회차 진행해
```

멈추려면 루프를 취소하거나 "루프 멈춰"라고 말하면 돼요.

## 한 회차의 크기

- 한 회차에 작업 하나를 끝내거나, 큰 작업이면 검증까지 할 수 있는 한 조각을 끝내요.
- 회차가 끝날 때 작업 트리는 깨끗해야 해요. 검사를 통과한 변경은 커밋하고, 통과하지 못한 반쪽 변경은 남기지 않아요(되돌리거나 더 작게 마무리해요).
- 긴 빌드나 VM 테스트는 백그라운드로 띄우고, 기다리는 동안 다른 일을 하거나 회차를 마쳐요. 결과는 다음 회차에 거둬요.

## 회차 순서

### 1. 상황 파악

```powershell
git status --short
git log --oneline -5
git log --oneline origin/main..HEAD
powershell -ExecutionPolicy Bypass -File scripts/wsl-build.ps1 status
```

그다음 [tasks.md](tasks.md)를 읽어요. 백그라운드 작업, 푸시 대기 커밋, 사용자 확인 필요, 진행 중인 작업 순서로 봐요. 작업 트리에 이전 회차가 남긴 변경이 있으면 그것부터 정리해요.

### 2. 끝난 결과 거두기

`status`에 아무것도 돌고 있지 않은데 tasks.md에 `실행 중`인 백그라운드 작업이 있으면, 그 작업이 끝난 거예요.

- 부팅 테스트: `build\boot-test\*.png`를 한 장씩 열어 봐요. `serial.log`에서 `robinos-session`, `quickshell`, `qml`, `Failed`를 찾아요.
- 설치 테스트: `build\install-test\*.png`와 `serial-live.log`, `serial-installed.log` 끝부분에서 `[install-test] FAILED`나 `passed`를 찾아요.
- ISO 빌드: WSL의 `/root/RobinOS/out/`과 `build/logs/`의 마지막 로그를 봐요.

결과를 tasks.md에 적어요. 통과했으면 해당 작업과 푸시 대기 커밋을 갱신하고, 실패했으면 원인을 찾아서 고칠 일을 `진행 중`으로 올려요. 같은 실패가 세 번 반복되면 다른 방법을 찾거나 작업을 `막힘`으로 두고 이유를 적어요.

### 3. 작업 고르기

이 순서로 골라요.

1. 방금 거둔 결과에서 나온 실패 고치기
2. `진행 중`인 작업
3. `할 일`의 맨 위 작업 (`막힘`은 건너뛰어요)

WSL에서 백그라운드 작업이 돌고 있으면 WSL 클론을 건드리는 일(빌드, 부팅 테스트, 설치 테스트)은 시작할 수 없어요. 그동안은 윈도우 쪽에서 할 수 있는 일을 해요. 코드 작성, `scripts/validate-project.ps1`, `scripts/wsl-build.ps1 check`(qmllint 포함), 문서 정리 같은 일이에요.

할 일 목록이 비면 [design.md](design.md)의 v0.1 범위와 [roadmap.md](roadmap.md)에서 다음 일을 찾아 tasks.md에 먼저 적고 시작해요.

### 4. 만들기

- 둘레 코드의 말투와 구조를 따라요. 사용자에게 보이는 글은 한국어(해요체)예요.
- `desktop/`, `bin/`, `scripts/`, `docs/`, `themes/`를 바꾸면 `scripts/sync-archiso-files.ps1`로 ISO 오버레이를 맞춰요. 이 스크립트가 바꾸는 `archiso/airootfs/etc/sddm.conf.d/10-robinos-theme.conf`의 줄 끝(CRLF)은 `git checkout`으로 되돌려요.
- 새 스크립트는 `git update-index --chmod=+x`로 실행 권한을 기록해요.
- 설계를 정해야 하면 직접 정하고 [design.md](design.md)에 결정과 이유, 날짜를 적어요. 제품 방향을 크게 바꾸는 결정만 사용자에게 물어요(아래 "사용자에게 넘길 때").

### 5. 검증

[testing.md](testing.md) 맨 위의 표대로 검사를 골라요.

- 빠른 검사(정적 검증, `bash -n`, `wsl-build.ps1 check`)는 그 자리에서 돌려요.
- ISO 빌드, 부팅 테스트, 설치 테스트는 먼저 커밋한 뒤(WSL은 HEAD를 가져가요) 백그라운드로 띄워요. 그리고 tasks.md의 백그라운드 작업 표에 시작 시각, 대상 커밋, 결과 위치를 적어요.
- 빌드와 테스트를 이어서 돌릴 때는 `build`가 끝난 뒤 `boot-test`처럼 차례로 해요. 한 번에 하나만 돌릴 수 있어요.

걸리는 시간 (이 PC, 윈도우 10 WSL 2 기준):

| 작업 | TCG (지금) | WHPX (T-002 이후, 목표) |
|---|---|---|
| ISO 빌드 | 9분 (2026-10-07 측정) | 같음 |
| 부팅 테스트 | 6분 (2026-10-07 측정) | 3분 |
| 설치 테스트 | 아직 모름, 1시간 넘을 수 있음 | 30분 안팎 |

새로 잰 시간은 이 표에 고쳐 적어요.

### 6. 기록

- [tasks.md](tasks.md): 작업 상태, 백그라운드 작업, 푸시 대기 커밋, 끝난 일(완료 목록 맨 위에 날짜와 커밋)
- [design.md](design.md): v0.1 항목 상태가 바뀌었거나 새 설계 결정을 했을 때
- 그 밖의 문서: [README.md](README.md)의 "같이 고칠 문서" 표를 따라요

### 7. 커밋

- 작업 단위로 커밋해요. 메시지는 한국어로, 첫 줄은 무엇을 했는지, 본문은 왜 그렇게 했는지 써요. 끝에 `Co-Authored-By` 줄을 붙여요.
- 커밋하기 전에 `scripts/validate-project.ps1`은 꼭 통과해야 해요.

### 8. 푸시

`git log origin/main..HEAD`의 모든 커밋이 필요한 검증을 통과했을 때(tasks.md의 푸시 대기 표가 비었을 때) `git push origin main`을 해요. 문서만 바꾼 커밋은 정적 검증이면 충분해요. 앞에 검증을 기다리는 커밋이 있으면 함께 기다려요. GitHub Actions는 수동 실행 전용이라 푸시해도 돌지 않아요.

### 9. 보고

회차 끝에 한국어로 짧게 알려요.

```text
이번 회차: <한 일>
검증: <돌린 검사와 결과, 백그라운드로 띄운 것>
다음: <다음 회차에 할 일>
사용자 확인 필요: <있을 때만>
```

### 10. 다음 회차 예약

`ScheduleWakeup`으로 다음 회차를 잡아요. 같은 `/loop` 문장을 그대로 넘겨요.

| 상황 | 기다릴 시간 |
|---|---|
| 바로 이어서 할 일이 있음 | 60초 |
| ISO 빌드를 기다림 | 600초 |
| 부팅 테스트를 기다림 | 420초 |
| ISO 빌드 + 부팅 테스트를 이어서 기다림 | 1020초 |
| 설치 테스트를 기다림 | 1800초, 끝나지 않았으면 다시 1800초 |
| 사용자 답을 기다리고 다른 할 일이 없음 | 루프 멈춤 |

기다리는 동안 할 일이 남아 있으면 기다리지 말고 그 일을 해요.

## 사용자에게 넘길 때

이런 일은 직접 하지 않아요. tasks.md의 "사용자 확인 필요"에 적고, 보고에서 알리고, 다른 작업을 계속해요.

- 관리자 권한이 필요하거나 윈도우 시스템 설정을 바꾸는 일
- 실기기 테스트처럼 사용자만 할 수 있는 일
- `git push --force`, 히스토리 다시 쓰기, 브랜치나 릴리스 지우기
- 돈이 들거나 계정 설정을 바꾸는 일
- 제품 방향을 크게 바꾸는 결정 (대상 사용자, 기반 배포판, 데스크톱 교체 같은 것)

개발 도구를 공식 출처에서 내려받는 건 괜찮아요. 내려받은 뒤 체크섬을 확인해요.

## 루프를 멈출 때

- tasks.md에 할 수 있는 일이 하나도 없고(전부 `막힘`이거나 사용자 확인 필요), 돌고 있는 백그라운드 작업도 없을 때
- 같은 문제로 회차 세 번 연속 진전이 없을 때 (원인과 시도한 것을 tasks.md에 적고 멈춰요)
